# DashBeam 直接源文件流式传输：时延与占用优化

日期：2026-11-12。实验代码 `7e037e1`，Android 描述符基础 `f7746e2`。

## 结论与交付边界

本轮已经实现并实际运行一个**不完整预 hash、不导入 blob 仓库、直接复用已打开源文件**的传输引擎。
接收端直接写目标文件系统上的部分文件，验证后原子提交；没有第二次整文件导出复制。
文件大小不再决定开始分享前必须读取的内容量：所有成功的 streaming 样本分享准备时，显式源读取计数都是 **0**。

这是显式实验 API/CLI，不是已安装客户端的改版。默认 GUI、旧 BlobTicket、配对和浏览器流程没有切换。
没有新发客户端安装包，也没有修改生产中继、现有身份或设置。Android 只是可定位普通文件的只读描述符 helper 完成编译，
尚未接 picker/JNI；不能声称手机现已免暂存。

最终 **十二组 × 三对 A/B = 72/72 个进程对样本、96 次文件接收**全部成功、逐字节一致且路径符合预期。
80 ms / 1 Gbit/s 下 64 MiB 直连完整返回中位 **5.742 → 1.904 秒**，强制中继 **6.423 → 2.752 秒**；
重复中继接收首次内部 payload 进度 **528 → 85 ms**。但低 RTT 小文件未全面提速，内存也不是全面下降。

## 传输流程究竟改了什么

| 阶段 | 现有兼容引擎 | 本次实验路径 |
| --- | --- | --- |
| 分享准备 | 已使用 TryReference，但仍要完整读取/hash，生成可用 BlobTicket | 仅 open/stat/seek 检查，产生私密 capability ticket |
| 开始下载 | 建立连接，blob sizes/collection 等请求后获取数据 | 一次 `Request(capability,max_bytes)` 后，`Offer` 和内容在同一有序流连续到达 |
| 文件读取 | blob store 的引用/导入路径 | 同一个已打开源句柄，64 KiB 分块顺序读 |
| 接收落盘 | 下载到 store，再 ExportMode::Copy 到用户目录 | 用户目录同卷私有 `.part`，边收边增量 hash，校验后硬链接原子无覆盖提交 |
| 重复接收 | 发送 share 可复用，但每次新建 receiver endpoint | 两端 share 可复用，receiver 还保留 endpoint 和同分享连接 |
| 服务端 | 原有不透明中继转发 | 继续原有中继，不新增对象仓库、整文件缓存或服务端 hash |

“取消完整预 hash”不是不校验：两端传输中增量 BLAKE3，接收端还验证精确长度、干净 EOF。
验证通过后先同步文件，再提交最终文件，再回送 Complete。提交后 ACK 丢失会返回已验证文件及回执状态，不自动重试或删除成品。

接收调用本身是对预算内单文件的明确同意，因此不再发送 Offer 后等待第二轮 Accept。
发送端先验证 capability 和双方大小预算，再获取源锁/检查文件/seek/read。元信息不合格、输出目录失败或取消时关闭连接，
由固定应用缓冲和 QUIC 窗口反压，不开额外无界预读任务。

## 测量方法

- 基线为已经优化过的兼容引擎：归档 `431e837`（产品逻辑 `2ef67ab`），不是最早的未优化版本。Iroh 1.0.3 / Blobs 0.103.0 不升级。
- 全部重编译/网络模拟在 `SER8-PVE-VM-102-Debian13-Dev`，独立目录 `/home/luoji/code/dashbeam-source-stream-20261112.wXzKWL`。
  原 `/home/luoji/code/dashbeam-macos` 脏源码不覆盖；仅共享已有 Cargo target 缓存。
- 隔离 internal Docker network，两个端点各 2 CPU/768 MiB，中继 1 CPU/768 MiB；tc/iptables 只在端点容器内配置。
  强制中继时阻断 peer UDP，并记录实际初始/最终选中路径。不是生产 GZ/SH 或真实 NAT 穿透实机测试。
- 合成文件热页缓存、每个样本冷 share；重复接收场景两种版本都保留 sender share，stream 额外复用 receiver 连接。
  A/B 顺序交替，源文件复用旧 fixture 的硬链接；新生成的 256 MiB fixture 非稀疏。
- 同内核 CLOCK_MONOTONIC 计时，用私有文件传递 ticket（10 ms 轮询）。没有 UI、信令设备列表、人工同意或 Android SAF 暂存。
- **Share → payload** 是 blob 第一次正进度事件 / stream 首帧首字节的内部代理，不是统一包级抓包时间点。
  两种观测的粒度不同；不能把差值全部等同于真正首个网络包提前量。
- **Share → export/commit** 是旧接收完成事件 / 新成功提交，作为输出可用代理；旧路径不显式 fsync，新路径同步文件。
  两者都不承诺父目录的断电持久性。
- **API return** 另列：旧版包含关闭 endpoint；stream 保留连接且等待完成回执的传输层确认，不能把全部返回时间差都归因于 payload 提速。
- 每次接收计时后逐字节比较，失败尝试保留在分母。三对适合工程判断，不报告 p95、统计显著性或互联网三秒 SLO。

其他关键判断：

- 256 MiB LAN 文件的分享准备 **160.098 → 31.231 ms**；准备 CPU **148.982 → 3.113 ms**。新路径不扫描文件，仍有 endpoint 启动成本。
- 80 ms 中继小文件的分享准备仍约 **0.56 秒**，没有因取消 hash 消失；既有在线/网络探测等待才是这里的后续目标。

- 50 Mbit/s 大文件主要受链路速率限制，完整返回只省约 0.13–0.14 秒；不是所有场景都会获得三倍提速。

### 两档窗口的补充对照

追加可调窗口 harness，用**同一个二进制**分别配置 2 / 8 MiB；两种网络每档两对 A/B，共 **16/16** 个样本，全部字节/路径通过。
不与最终十二组混合统计。下面只对照 streaming 两档，均为各自两次中位数；原始数据见 `results/profiles-{2m,8m}/`。

| 64 MiB / 80 ms 强制中继 | 2 MiB 窗口 | 8 MiB 窗口 |
| --- | ---: | ---: |
| 50 Mbit/s，Share → payload | 0.910 s | 0.922 s |
| 50 Mbit/s，Share → API return | 13.069 s | 13.028 s |
| 50 Mbit/s，Sender max RSS | 23.20 MiB | 33.88 MiB |
| 50 Mbit/s，Receiver max RSS | 18.39 MiB | 23.78 MiB |
| 1 Gbit/s，Share → payload | 0.912 s | 0.916 s |
| 1 Gbit/s，Share → API return | 4.532 s | 2.753 s |
| 1 Gbit/s，Sender max RSS | 22.12 MiB | 33.57 MiB |
| 1 Gbit/s，Receiver max RSS | 19.58 MiB | 18.96 MiB |

这给出一个实用选择：**本次 50 Mbit/s 中继条件下，2 MiB 窗口基本保留速度，sender 低约 10.7 MiB RSS**；
优先低占用时可在实验 CLI 用 `--transport-window-mib 2`。高 BDP 吞吐优先时选择 8 MiB，64 MiB 文件再快约 1.78 秒，代价是更多 sender 在途内存。
接收端 RSS 并非窗口越小就保证越低。每档只有两对，不能把十几毫秒差异当稳定优势，也没有实现自动最优档位或安装版设置项。

磁盘按 10 ms 抽样统计本次 app temp + output 内的普通文件，排除源文件，按 `(device,inode)` 去重，避免部分文件/最终硬链接重复计数。
既报告逻辑长度也保留 allocated blocks；后者不能识别共享 reflink extents，抽样也可能漏过短暂副本，不作为硬上限。
Linux 文件系统上的降低不能直接推广为 APFS 上同等物理磁盘节省。

CPU、RSS 来自整个测试进程，包含 runtime/采样等开销；sender 全程统计还覆盖等待接收端核验的时间。
`rchar` 是 read 系统调用的逻辑字节，不统计 mmap 页读取，也不是物理磁盘 IO；不靠旧版 rchar 小就推断“旧版没 hash”。
`first_receive_cpu_ms` 不含之后逐字节比较；进程最终 maxrss/累计统计可以包含它。
中继 CPU 是容器 cgroup 使用量差，含少量探针 exec 成本；memory.peak 是全容器累计高水位，不是单文件峰值或 relay 进程 RSS。
这些是资源代理，**没有测量瓦数或实际电池续航**。

## 实验中的两次重要纠偏

### 1. 只去掉预 hash / 仓库还不够

早期带 Accept 的原型跑完十组 × 三对：**60/60** 进程对样本、**84** 次文件接收，全部字节/路径通过。
它更早出现数据，减少额外落盘，但不少 WAN 小文件的 API 完整返回反而略慢，不能直接宣称全面提速。
随后把接收预算并入首次请求，去掉 Offer → Accept 一次应用往返，同时保持授权、预算、文件验证和完成回执。
旧结果单独保留在 `results/matrix-accept/`。

### 2. 1 MiB 小窗口会制造新的慢速

无 Accept / 1 MiB 原型另跑 80 ms / 1 Gbit/s、64 MiB 的 direct/relay 两组，每组两对，共 **8/8** 通过。
直连 API 返回中位约 **5.731 → 6.733 秒**，中继约 **6.415 → 7.418 秒**，均回归约一秒。
所以没有把“小缓冲”等同于优化，而是继续定位流控窗口。

源码核验：Iroh 1.0.3 的 QuicTransportConfig 继承 Noq 1.1.0 默认值，单流接收窗口 1,250,000 B，
发送窗口 10,000,000 B；我们最初把三个窗口都压成了 1 MiB，反而限制了在途数据。
依赖源的发送 SendBuffer 和接收 Assembler 从空容器初始化；窗口是允许在途/缓冲的上限，不会立即分配同样大小的连续内存。
当前改成默认 **8 MiB**，API 允许 **64 KiB–16 MiB**；CLI 可显式选择 1–16 MiB。
64 KiB 应用帧不变，且没有全文件 read-ahead task。8 MiB 是占用和吞吐的折中，不是进程 RSS 上限，也不承诺任何 RTT 下跑满 1 Gbit/s。

最终默认值必须以本报告的实测 RSS 与吞吐同时评价。1 MiB 反例保留在 `results/high-bdp-1m/`，不是藏掉的失败。

初次 smoke 还出现一次 harness 配置错误：legacy ticket 未显式携带地址，隔离 discovery fixture 又返回 404，导致无地址可连。
修正为 RelayAndAddresses 后重跑；`smoke-v1` 已排除正式性能统计，原始失败记录保留。它不是产品修复收益。
早期定向测试也曾因 DEV 的 umask 0002 导致输出目录可被组写而失败；将测试夹具局部设成 0700 后通过，未放宽产品目录权限校验。

这个累计数只表示这些 suite 的成功总量，不把它们混成同一种配对或同一个版本的性能分布；初始错误 smoke 和开发中失败的测试不在其中。

优先的下一阶段是**把已验证的流式 handler 注册到现有常驻控制 endpoint/router**，消掉每次分享的新节点上线等待；
用现有加密配对信令协商 streaming 能力并发送最小文件信息，不再增加第二套服务端设备注册框架。
旧端/浏览器、目录/多文件、特殊文件系统继续明确走旧 BlobTicket 兼容路径，不通过失败后悄悄双发或自动重试。
迁移时仍要保留 transfer ID 对旧任务清理的隔离，避免取消 A 误停 B。

Android 再把持有 URI 授权的描述符同步 dup 成同进程 Rust 独占源，接上 picker/JNI/生命周期；管道和未知大小 provider 不能伪装为普通文件。
完成 UI、两端能力协商、文本自动复制边界和实机回归后，才应重新打包全部客户端。这一轮没有用引擎 benchmark 冒充安装版验收。

此前的**可选硬盘密文 spool**设计仍可单独推进，但它能解耦快发送端/慢接收端，不会凭空提高慢端的接收速率；
本轮优先消除不必要的读/写/等待，不默认增加服务器文件暂存、配额、清理和恢复负担。
