# DashBeam 时延对比：DEV 实测报告

日期：2026-11-11。主实验 **10 种条件 × 5 对旧/新版 = 100 次传输**，全部成功，
输出文件逐字节一致，连接建立与载荷完成时的所选路径均符合预期。
另完成 **10 次不同显式 home relay 传输**、**30 次导出缓存候选对比**，均通过字节及路径核验；
两项补充实验独立统计，不混入主矩阵的 100 次。

最明确的结论：现有兼容优化确实减少了启动等待。80 ms RTT、50 Mbit/s 的
强制中继场景，从发起分享到出现有效载荷进度的中位耗时，从 **2.662 秒降到
1.129 秒**；载荷本身的持续传输速度基本未变。

## 测的是什么

- 旧版：`f3253bbbf6c1028821e2a66602ede9557cff4113`。
- 新版：`2ef67abf2e100f32db9aca7834397e705250053e`，即已发布 `v0.7.1-local.4`
  的产品源码；不是最新上游新协议原型。两版均为 Iroh 1.0.3 / Blobs 0.103.0。
- 在 Debian DEV 的独立 Docker 网络内运行真实 engine、真实 QUIC/中继传输与磁盘导出。
  应用命令层的 Strict relay 解析及 metadata/download 先后关系由 harness 等价编排。
- 每种条件旧/新各 5 次，AB/BA 交替；每次新进程、新 Endpoint、随机临时身份、独立 store
  和输出目录。两版统一预读相同输入，因此是**热文件页缓存、冷进程/端点**，不是冷硬盘。
- 两端各 2 CPU、2 Tokio worker，中继 1 CPU，每容器限 768 MiB。相同 Rust 工具链、
  锁文件和 release profile。源码插入前/后哈希、二进制哈希、网络规则及 qdisc 计数留档。
- 单中继主矩阵使用真实 HTTPS、自签测试 CA 和 UDP 7842 地址发现，不经过 TCP 代理。
  CA 只传给实验进程，没有加入主机信任。自建中继认证没有在本实验中模拟。

“启动接收”在本报告中特指首个正数 **Blobs 内部载荷进度代理**，不是抓包得到的
第一字节。普通 UI 进度另有节流，不能拿它直接代替网络首字节。端到端时钟包含
20 ms 轮询的私有票据交接，不包含人工选择接收端、信令服务、GUI 缩略图或 Android SAF。

## 主实验结果

下表均为 5 次中位数，单位秒。“完整返回”包含载荷下载、导出、元信息收尾及端点关闭，
但独立的逐文件字节校验在该计时之外。它不代表文件已达到断电不丢失的 fsync 保证。

| 条件 | 文件 | 旧：启动接收 | 新：启动接收 | 旧：完整返回 | 新：完整返回 |
| --- | --- | ---: | ---: | ---: | ---: |
| 直连，2 ms / 1000 Mbit/s | 1 MiB | 0.114 | 0.097 | 0.131 | 0.113 |
| 直连，2 ms / 1000 Mbit/s | 64 MiB | 0.136 | 0.136 | 0.751 | 0.749 |
| 直连，2 ms / 1000 Mbit/s | 256 × 4 KiB | 0.137 | 0.113 | 0.183 | 0.156 |
| 直连，80 ms / 50 Mbit/s | 1 MiB | 0.719 | 0.469 | 1.277 | 1.029 |
| 直连，80 ms / 50 Mbit/s | 64 MiB | 0.774 | 0.485 | 12.505 | 12.223 |
| 中继，2 ms / 1000 Mbit/s | 1 MiB | 0.889 | 0.350 | 0.912 | 0.382 |
| 中继，80 ms / 50 Mbit/s | 1 MiB | 2.662 | 1.129 | 3.221 | 1.691 |
| 中继，80 ms / 50 Mbit/s | 64 MiB | 2.663 | 1.122 | 14.716 | 13.178 |
| 中继，150 ms / 20 Mbit/s / 0.5% 丢包 | 16 MiB | 4.261 | 1.791 | 37.605 | 34.019 |
| 中继，80 ms / 50 Mbit/s，元信息模拟超时 | 1 MiB | 5.270 | 1.122 | 5.830 | 3.574 |

这里的 RTT 为发送端到接收端的名义往返延迟：两端 egress 各施加一半，中继不再额外叠加。
限速是接口 egress 上限，不是承诺的应用吞吐。各场景 ping 校准和每次 qdisc 前/后计数见原始记录。

### 改善有多稳定

按每对的“旧耗时减新耗时”计算，启动接收节省量的中位数/最小/最大分别为：

- 直连 1 MiB / 80 ms：**254 ms**，范围 232–267 ms。
- 中继 1 MiB / 80 ms：**1536 ms**，范围 1508–1552 ms。
- 中继 64 MiB / 80 ms：**1542 ms**，范围 1528–1570 ms。
- 受损中继网络：**2476 ms**，范围 2459–2860 ms。
- 元信息模拟超时：**4148 ms**，范围 4133–4160 ms。

这与直接相减两个中位数不是同一种统计量。每组只有 5 对，适合看中位数和范围，
不用于宣称可靠 p95、总体显著性或互联网三秒 SLO。LAN 小文件差异只有十几毫秒，
存在调度和准备抖动；LAN 大文件的差异几乎为零。

## 时间究竟省在哪里

1. **Strict 中继不再先建一个临时探测端点。** 在 80 ms 单中继样本中，旧发送/接收
   relay resolve 各约 0.59 秒；新版约为本地配置解析成本，真实端点仍正常建立连接。
2. **元信息不再串行挡住 payload。** 80 ms 直连小文件的主要收益约 0.25 秒；中继
   中这部分与两端临时预探测一起构成约 1.5 秒收益。
3. **不能给 online/import 并行单独记一笔“理论节省”。** 旧版已经在导入前 bind；
   Iroh 在线流程早已在后台推进。实测准备阶段没有显示出可单独归因的大额收益。
4. **持续传输没有明显提速。** 64 MiB / 80 ms 中继的 payload get 中位数为旧版
   12.156 秒、新版 12.161 秒，几乎一致。完整流程缩短约 1.54 秒来自启动。
5. **元信息超时仍会影响最终完成。** 第 10 组是在 advisory timeout 内注入 sleep，
   不是网络上故意卡住 ALPN。新版约 1.12 秒已出现载荷进度，但完整返回仍需约
   3.57 秒，保留了成功下载后等待 advisory 的时序。产品中的文本校验与 GUI 完成门控
   由源码及此前单元测试说明；本 harness 没有执行文本或 GUI 验收。

### 丢包会明显拖慢持续传输

0.5% 丢包组五对的完整返回如下，单位秒：

| Pair | 旧版 | 新版 | 新版 payload get 相对旧版 |
| --- | ---: | ---: | ---: |
| 1 | 26.309 | 22.929 | +0.508 |
| 2 | 37.605 | 34.086 | −1.050 |
| 3 | 41.084 | 34.019 | −4.611 |
| 4 | 26.576 | 22.155 | −1.768 |
| 5 | 40.390 | 38.782 | +0.674 |

五对端到端全部更快；载荷阶段两次略慢、三次更快，没有观察到一致的吞吐回归，
但也不能声称吞吐全面提升。一次运行中的只读容器观察显示 CPU 约 0.8–2.9%、
内存均小于 38 MiB；这是单次观察，不是全程资源分布或功耗测量。

磁盘缓存/缓冲机制不属于当前兼容优化。现有实验没有实现新的服务端密文磁盘 spool，
因此这些数据不能证明 spool 的收益或其崩溃恢复能力。

## 迭代中排除的错误方向

最初 HTTP+socat 的实验环境没启用 QAD，但客户端仍按默认配置探测 UDP 7842，
出现约 3 秒的 online 和约 1 秒的 close 等待。补齐 HTTPS + QAD 后，这些等待大幅消失，
没有任何产品代码改动。初始 smoke 和中断的 partial-main 不计入正式结果。

正常低 RTT 下，close 约 0.1–2 ms；80 ms RTT 下约 40–80 ms。受损网络中偶尔可到
1 秒，这是正常关闭确认的尾延迟。本轮没有删掉 close、缩短校验或取消清理来提速。

单中继冷启动仍有约 250 ms 的 online 成本；源码显示锁定 Iroh 版本的首次完整
net-report 在只有一个 relay 时会等带 200 ms offset 的 HTTPS probe。这是后续“常驻共享
端点/复用”的优化动机之一，不应直接删除 `online()` 等待。

### 补充迭代：父目录缓存未采纳

在独立 `optimized-v2/` 中测试每次 export 缓存已创建父目录，减少多小文件的重复
`create_dir_all`。新增/既有导出测试 **14/14 通过**，LAN 单文件、LAN 256 小文件、
WAN 中继单文件各 5 对，共 **30/30 传输通过**。

256 小文件的导出后处理阶段从中位 **34.193 ms** 降到 **25.390 ms**，配对节省中位
**8.137 ms**（4.552–12.224 ms）。但该组完整返回并没有稳定改善，配对中位反而慢
**3.823 ms**，范围为慢 9.519 ms 到快 38.037 ms；两个单文件场景没有导出阶段收益。

更重要的是：同次导出期间若外部删除已缓存目录，候选不再像原实现那样重建它。
因此**不合入产品**，仅保留实验 patch、原始数据和测试记录。不能把这 8 ms 当作客户端
已经获得的端到端收益，也不为此发布新客户端。

## 补充：不同显式 home relay

另开两个独立 HTTPS/QAD relay，不建 relay mesh；发送端仅配置 A，接收端仅配置 B，
阻断两端 peer UDP。16 MiB、80 ms RTT、50 Mbit/s、无丢包，旧/新各 5 次，**10/10 通过**。
出票时发送端 connected-home 快照非空且仅 A；接收端 get-done 快照观察到 B、没有 A；
载荷首尾所选路径均为 relay，输出逐字节一致。

| 指标（5 次中位数，秒） | 旧版 | 新版 |
| --- | ---: | ---: |
| 分享准备完成 | 1.125 | 0.562 |
| 发起分享 → 有效载荷进度 | 2.643 | 1.118 |
| 发起分享 → 完整返回 | 5.936 | 4.420 |

配对启动节省中位 **1.528 秒**，范围 1.487–1.558 秒；完整返回配对节省中位 **1.524 秒**。
这证明所测条件下不同显式 home 可以完成真实传输，不需要先搭建 relay mesh。
但快照与 `relay/IP` 标记不是连续包级追踪，不能据此断言 payload 必定依次经过 A、B；
更不等于两端同时配置双 URL 的自动选择、GZ↔SH 地理链路、手机休眠或生产认证已经验收。

## 边界与下一步

- 本报告主矩阵是单中继、同一 Linux 内核、合成文件、自动交接。不是手机到 Mac、
  跨 GZ/SH 公网、不同 NAT、移动端休眠、GUI、通知或安装版验收。
- 不同显式 home 已有上述隔离补充实验；两端都设置 GZ/SH 的自动 home 选择、
  公网陈旧地址恢复及手机到 Mac 仍需分别验证。
- 当前兼容方案仍需完整 collection hash 才能生成 BlobTicket；大文件准备与 Android
  SAF 完整 staging 的瓶颈尚未消除。不能宣称已实现“开始分享即发送首字节”。
- 下一阶段按已有设计优先考虑共享 Endpoint/连接复用、最小 Offer/Accept、边读边传
  边增量校验，再实现有预算与恢复语义的密文硬盘 spool。这些属于新流程，不混入
  本次兼容版的测试结论。
